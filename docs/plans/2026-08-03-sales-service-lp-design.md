# 営業用サービスLP 設計ドキュメント

- 日付: 2026-08-03
- 対象: `/lp/index.html`（仮配置。最終的な配置先は未決 — 後述「未決事項1」）
- ステータス: 実装完了・デザイン承認済み（配置先の確定待ち）

## 目的

営業活動で商談前に送るURLとして使える、Balcony のサービス全体像が分かるLPを作る。相手が一人で読み切り、会う前に「この会社と話す価値がある」と判断できる状態にする。

既存 `/service/` は内容が抽象的（「多角的に支援します」）で、誰のどの課題をどう解決するかが書かれておらず営業には使えない。本LPがその役割を担う。

## 確定した論点（ユーザー確認済み）

| # | 論点 | 決定 |
|---|------|------|
| 1 | 使われ方 | **商談前に送るURL**。読み物として一人で完結する。滞在3〜5分 |
| 2 | 読者 | CxO・経営層／情シス部長・DX推進責任者／SIer・パートナー企業の**3層すべて** |
| 3 | 主力商材 | **セキュリティ脆弱性診断**（看板） |
| 4 | `/security/` との役割分担 | **会社が主・診断が看板**。新LPは会社の信頼を作り `/security/` へ送客する入口 |
| 5 | 人材紹介の扱い | Balcony 主体で構成し、人材領域で **PORTAMENT との協業をロゴ付きで明示** |
| 6 | デザイン | **グリーン基調＋セキュリティのみネイビー×ティール**のブロック |
| 7 | 料金レンジ | **掲載しない**。代わりに期間目安と「初回相談・見積は無料」をFAQで明示 |
| 8 | 代表の経歴 | **掲載可**。正面から出す |

## アプローチ

3案を比較し、A案を採用。

| 案 | 内容 | 判断 |
|---|------|------|
| **A. 「信頼の階段」型（採用）** | 何者か → 誰がやるか → 何ができるか → 何が一番強いか → 本当にやったのか の順に信頼を積み上げる | 「商談前に送るURL」「会社が主・診断が看板」の2決定と正面から整合。3層すべてに効く |
| B. 課題起点・分岐型 | ヒーロー直下で読者を3つの課題に仕分けてアンカー遷移させる | 読了率は上がるが会社の全体像が伝わらない。「会社が主」と噛み合わない |
| C. 営業資料のWeb化 | 会社紹介デッキをそのままスクロールに落とす | 情報密度は高いが平板で、レッドチーム経験のような決定的な差別化が埋もれる |

案Cの情報密度（サービス一覧表・進め方）と、案Bの課題起点の言い回しは、案Aの中にセクションとして部分的に取り込む。

## セクション構成（9枚）

### 1. Hero

現行の「新しい価値を定義する」は理念としては良いが営業では相手が動けない。具体に振る。

> **経営とITの、両方が分かる。**
> 戦略立案からシステム実装、脆弱性診断、人材まで。
> 少数精鋭のプロが、課題の入口から出口まで一社で伴走します。

- 直下に5領域を横一列のチップで配置し、「何ができる会社か」を3秒で伝える
- CTA 2本: `相談する` / `セキュリティ診断を見る`

### 2. 導入実績（Trusted By）

早い段階で信用を渡す。営業LPで最も効くセクションのため前方に置く。

- 業種と規模のみ。**社名・ロゴは掲載しない**（`/security/` v1 で確立した方針を継承）
- 誇張表現（多数・続々等）は使用しない
- バッジ: `金融機関（信用金庫）` `システムインテグレーター` `大手製薬` `大規模物流システム`

「規制業種が直接契約している」という事実が、少数精鋭の会社にとって最大の信用材料になる。

### 3. 選ばれる理由（4つ）

| # | 理由 | 裏付け |
|---|------|--------|
| 01 | 経営とITの両方が分かる | 代表が事業会社のDX推進責任者を**現任** |
| 02 | AIレッドチーム経験者が在籍 | OpenAI・Grok のレッドチーム経験 |
| 03 | 戦略〜実装〜運用〜人材が一社で繋がる | 5領域を横断できる体制 |
| 04 | 少数精鋭ゆえの速さと適正価格 | 意思決定の階層が無い |

### 4. 代表 岸田邦裕

少数精鋭の会社では、会社の実体は「人」。ここは削らず正面から出す。

リクルート・カチタスでの20年、基幹システム刷新によるコスト削減、エンジニア組織のゼロからの構築・拡大、生成AIを活用した業務アプリケーション開発、Web3領域の新規事業立ち上げ、全社ITガバナンス整備。現在もカチタスでDX推進責任者を兼務。

この幅の広さ自体が「戦略〜実装〜運用が一社で繋がる」の証拠になる。

## デザイン仕様

`/security/` v2 の刷新方針（2026-07-06 追記分）を継承する。**装飾で語らず、情報で語る。**

| 要素 | 仕様 |
|------|------|
| 基調 | コーポレート共通のグリーン `#6B8F71` |
| セクション背景 | 白 `#FFFFFF` ↔ 淡緑 `#EEF1EA`（`--g-light`）を厳密に交互 |
| セキュリティブロック | ネイビー `#15263A` × ティール `#0E7C74` / `#35B5AE` |
| セクション境界 | 波形ディバイダー（高さ44px）。形状2種を交互に反転 |
| カード | 白背景＋1pxボーダー `#D8DDD4`、角丸、影なし。ホバーはボーダー色の変化のみ |
| フォント | Noto Sans JP / Plus Jakarta Sans（SITE_RULES §3.2 準拠） |
| 禁止 | パーティクル、グロー、グリッチ、装飾背景数字、巨大背景文字、絵文字アイコン（インラインSVGを使う） |

### 背景色の選定理由

初版は淡セクションに共通CSSの `--bg` `#F7F5F0` を使ったが、白との差が約3%しかなく**セクションの区切りが視認できなかった**（レビューで「のぺっとしている」との指摘）。`--g-light` `#EEF1EA` へ変更し、差を約7%かつ緑寄りにして境界を成立させた。

### 波形ディバイダーの実装

セクション境界9箇所（Hero含む）に配置。既存 `page-hero-wave` と同じ作法。

- 波形 `div` の**背景に前セクションの色**を敷き、**path の `fill` を次セクションの色**にする。これで次セクションが波打って始まる
- 形状は2種を交互に使う（同一形状が9回続くと単調になる）
  - A: `M0,26 C400,46 800,2 1440,22 L1440,44 L0,44 Z`
  - B: `M0,22 C400,2 800,46 1440,26 L1440,44 L0,44 Z`
- 背景クラスは `.on-white` / `.on-tint` / `.on-navy` の3種。`fill` は16進数直書き（SVG属性なのでインラインスタイル警告に該当しない）
- 波形の導入に伴い、セクション上端の1pxボーダーは削除した（線と波の二重は過剰）

## 経緯

### 資料の読み取りについて

PDFは `pdftotext` では日本語が抽出できなかった（ToUnicode CMapを持たないCIDフォント。英数字のみ取得可能）。**pymupdf (`fitz`) では全8ファイル・156ページの日本語抽出に成功**した。同種のPDFを扱う場合は pymupdf を使うこと。

Figma Site（`hachidori-hr-note.figma.site`）は静的HTMLに本文がなく、`/_components/v2/<hash>.js` にコンテンツが入っていた。このJSを取得し `\uXXXX` エスケープをデコードして本文を抽出した。

## 確定した論点（ユーザー確認済み）

| # | 論点 | 決定 |
|---|------|------|
| 9 | Balcony の立ち位置 | 各サービスの**営業を受託**している。PORTAMENT のサービス群は「自社サービスとして直接提供」されている |

| 11 | プロダクト名の表記 | **出さない**。機能名で書く（「バックオフィス代行」「AI人事担当」等）。プロダクト名から提供元が特定されるのを避けるため |
| 12 | 既存 `/lp/` との関係 | **拡張して統合**。1枚で全サービスを見せる |

| 15 | セキュリティ脆弱性診断 | 俯瞰表とネイビーブロックの**両方に掲載**。看板扱いを維持 |

## 実績の帰属についての線引き

社名を出さない方針でも、**他社の実績を自社実績として書くことはしない**。

| 書ける | 書けない |
|--------|----------|
| 「取り扱うAI・自動化サービスは200社以上で利用」（サービスの実績。提供主体を問わない事実） | 「弊社の売上4.4億円」（パートナーの財務実績） |
| 機能・料金・削減効果（最大80%自動化、従来の1/5のコスト 等） | 特定企業の支援実績（パートナーの実績） |

後日「これは御社の実績ですか」と問われた際に説明できる状態を保つための線引き。

## 平坦さ（「のぺっと感」）への対応

3回の指摘を受けて段階的に対処した。原因と対策の対応は以下のとおり。

| 原因 | 対策 |
|------|------|
| 白と淡セクションの差が3%しかなく区切りが見えない | 淡セクションを `#EBF3FF` に変更（差を拡大） |

| 影がなく要素が面に貼り付いている | カード4種に控えめな影＋ホバーで持ち上げ |
| 15枚のカードが均一 | 1サービスのみの分類を全幅の横長カードに |

### レビューから得た指針

- **背景の交互は、色の差が視認できなければ機能しない。** 3%程度の差では区切りとして働かない
- **同じ情報を表とカードで2回見せない。** 情報密度を上げる意図が、逆に冗長さとして受け取られる
- 文章は「1セクション1文」を上限の目安にする

## 実装メモ

### 意図的な判断

| 項目 | 判断 | 理由 |
|------|------|------|
| 配置 | `/lp/` に仮配置 | 配置先が未決のため、公開中の `/service/` を上書きしない。移動は容易 |
| sitemap / llms.txt | **未登録** | 配置未確定の段階で検索エンジンに積極的に出さない。URLを送れば閲覧はできる |
| 代表の写真 | **使わない** | 既存 `/company/` は代表写真としてストック画像（`stocksnap-apple-…`）を使用している。本人写真でないものを代表として出さず、経歴のテキスト構造化で見せる |
| FAQ の実装 | `<details>` / `<summary>` | 共通 `js/main.js` にアコーディオン制御が無いため、JSなしで動く素の要素を使う |
| ヒーロー背景 | `pexels-bricks-2181920_1920.jpg` | 既存画像から選択。暗いオーバーレイでコピーの可読性を確保。差し替え可能なようHTML側で指定 |
| `.page-hero-bg` の併記 | ヒーロー背景に両クラスを付与 | `js/main.js` の背景ロードアニメーションが `.page-hero-bg` を参照しているため共用する |
